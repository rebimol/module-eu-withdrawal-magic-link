## 0.1.2

+ New: **Admin toggle `Stores → Configuration → MageMe Extensions → EU Withdrawal → Magic Link (Pro) → Enable Magic Link`** (config path `mageme_eu_withdrawal/magic_link/enabled`, store-view scope). When set to **Yes** (default after install), the withdrawal CTA in order/shipment confirmation emails uses the tokenised one-click `?t=TOKEN` URL. When **No**, the Pro resolver delegates to Lite's `LookupWithdrawalLinkResolver` and the CTA falls back to the lookup-form URL `/withdraw-contract/` — same behaviour as a Lite-only install. Useful for staged rollouts (enable per store-view) or for merchants who installed Pro but prefer the Art. 11a(1) lookup-form floor without uninstalling. Toggling the flag does NOT revoke previously-issued tokens — they keep resolving until their TTL expires.
* Change: **Module gutted to URL-resolution only.** All email infrastructure has moved to Lite (`MageMe_EUWithdrawal` 0.12.9). What this Pro module ships now is a single class `Model\Email\MagicLinkWithdrawalLinkResolver` and one DI `<preference>` that swaps Lite's default `WithdrawalLinkResolverInterface` binding from `LookupWithdrawalLinkResolver` (returns `/withdraw-contract/`) to a tokenised `/withdraw-contract?t=TOKEN` resolver. The token is issued via the existing `MagicLinkService::issueOrReuseForOrder()`; behaviour and TTL semantics are unchanged. The observer, snippet block, phtml, four sales-email overrides, `etc/email_templates.xml`, `etc/events.xml`, and the 3 unit tests on the deleted observer are removed from this module — they now live in Lite. Pro merchants upgrading from 0.1.1 see no behavioural change in the customer-facing CTA: same templates, same observer, just upgraded URL.
- Files removed: `Observer/AppendMagicLinkToOrderEmails.php`, `Block/Email/WithdrawalLinkSnippet.php`, `view/frontend/email/sales_{order,shipment}_new{,_guest}.html` (4 files), `view/frontend/templates/email/withdrawal_link_snippet.phtml`, `etc/email_templates.xml`, `etc/events.xml`, `Test/Unit/Observer/AppendMagicLinkToOrderEmailsTest.php` and 2 related test fixtures.
- Files added: `Model/Email/MagicLinkWithdrawalLinkResolver.php` (~25 LOC).
+ New: `etc/di.xml` `<preference for="MageMe\EUWithdrawal\Api\Email\WithdrawalLinkResolverInterface" type="MageMe\EUWithdrawalMagicLink\Model\Email\MagicLinkWithdrawalLinkResolver"/>` — the single hook that flips Lite's CTA URL from lookup-form to magic-link.
- Note: composer.json now requires `mageme/module-eu-withdrawal: >=0.12.9 <1.0` (was `>=0.11`) since the `WithdrawalLinkResolverInterface` and the email observer ship in Lite 0.12.9. Merchants on older Lite cannot install this version; bump Lite first.

## 0.1.1

* Change: **Stop auto-overriding Magento `sales_email/order/template` and `sales_email/shipment/template` defaults.** The four `<sales_email>` `<order>` / `<shipment>` `<template>` / `<guest_template>` entries are removed from `etc/config.xml`. Production Hyva / Klaviyo / SendGrid / custom-themed merchants almost always ship their own branded order-confirmation and shipment-notification templates; the previous module-level template override would silently overwrite them on first install, leaving the merchant with vanilla Magento email styling instead of their brand.
* Change: The four module-shipped templates (`mageme_eu_withdrawal_sales_email_order_template`, `_guest`, `mageme_eu_withdrawal_sales_email_shipment_template`, `_guest`) remain registered via `etc/email_templates.xml` — they are still visible in admin **Marketing → Email Templates → New Template → Template = "MageMe EU Withdrawal — …"** as opt-in starters for merchants who want a vanilla-Magento-with-CTA template without writing their own. Wire-up at **Stores → Configuration → Sales → Sales Emails → New Order Email Template / New Shipment Email Template** per store-view.
+ New: `Observer\AppendMagicLinkToOrderEmails` continues to inject `withdrawal_link_url` (string) and `withdrawal_link_html` (rendered snippet HTML) into every `email_order_set_template_vars_before` and `email_shipment_set_template_vars_before` event — **regardless of which template Magento renders**. Merchants surface the CTA by adding this snippet anywhere in their custom template:
  ```html
  {{depend withdrawal_link_html}}
  <tr class="email-withdrawal">
      <td>{{var withdrawal_link_html|raw}}</td>
  </tr>
  {{/depend}}
  ```
+ New: README "Adding the withdrawal CTA to your email template" section — copy-paste snippet, three integration paths, and a "what happens if you upgrade an existing pre-release install" section.
- Note: Existing pre-release deployments that relied on the auto-active template override will no longer auto-display the CTA after upgrade. To restore: either (a) wire the opt-in template via the admin path above (one config change per store-view), or (b) add the snippet block to the merchant's custom template. Pre-release-only breaking change — module is at 0.1.x with no production deployments.

## 0.1.0

+ New: Initial Pro tier add-on extracted from `MageMe_EUWithdrawal` (Lite) phase-35 split refactor (2026-04-30). Adds one-click guest withdrawal access on top of Lite's lookup-form floor: signed 72h `?t=TOKEN` magic-link tokens (rolling 24h after first click), persisted in `mm_eu_withdrawal_magic_link`, plus four sales-email overrides that inject a "Withdraw from contract" CTA into Magento's order-confirmation and shipment-notification emails for both logged-in and guest customers. Pro DI binds `MageMe\EUWithdrawal\Api\Token\MagicLinkServiceInterface` to local `MagicLinkService` so Lite's customer-identity factory, lookup controller, and frontend form blocks resolve `?t=` URL params to bound order entities. Lite alone (without this module) still satisfies Art. 11a(1) "as easy as conclusion" via the lookup form (CJEU DHL/Amazon precedent treats lookup forms as legally sufficient); this module is a UX upgrade, not a compliance MUST.
